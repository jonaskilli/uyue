# AI 音效 · 分类体系

用「禁止正则 + 分类正则 + 音效正则」三层漏斗，替代按段落调用 AI 识别音效。
本目录是该方案的**分类数据层**，不含运行时代码。

---

## 1. 为什么要这套东西

现状 `AiEffectAnalyzer` 对每一批段落调用一次大模型（先提关键字、再从候选里挑），
有费用、有延迟、离线不可用、结果不可复现。

替代思路：**把「文本 → 音效」这件事拆成三层确定性规则**。

```
段落/句子
  │
  ├─ ① 对每个分类 C：
  │      C.blockRegex     命中 → 淘汰 C      ← 本分类专属禁止层
  │      C.classifyRegex  未命中 → 淘汰 C    ← 本分类专属分类层
  │
  ├─ ② 存活的 1~N 个分类
  │
  └─ ③ 在这些分类下挂的所有音效 → 跑各自正则 → 命中 → AiEffectPick
```

### 两条核心原则

**a) 禁止层是 per-分类的，不是全局一票否决**

同一个词对不同分类是相反待遇：

| 词 | `A01 刀剑挥击破空` | `E08 记忆回忆` |
|---|---|---|
| 回忆 | ❌ 禁止（回忆里的打斗不该响） | ✅ 不禁止（库里就有「回忆声雾化」） |
| 梦里/幻觉 | ❌ 禁止 | ✅ 不禁止（「幻听耳语层」） |
| 如果/倘若 | ❌ 禁止（假设的战斗没发生） | 视情况 |

所以不存在一个全局禁止层——**禁止条件只有相对于某个分类才有意义**。

**b) 分类必须细，禁止层才敢写严**

分类越细 → 每个分类语义边界越窄 → 禁止层可以写得很狠而不误伤 →
淘汰率越高 → 第 ③ 层要跑的正则越少。三者是正循环，不是取舍。
（粗分类下禁止层必然两难：写了误杀，不写形同虚设。）

## 4. 数据结构

### 4.1 `ai_effect_categories.json`

```jsonc
{
  "meta": { "uniqueEffectCount": 3830, "coverage": "59%", "blockFilledCount": 83, ... },
  "domains": { "A": "冷兵器战斗", ... },

  // 所有分类共用的禁止集（从大正则提炼，222 词去重后）
  "commonBlock": {
    "global": { "count": 6,   "regex": "(?:俗话|古话|古语|常言道|有道是|老话)", "words": [...] },
    "tail":   { "count": 3,   "regex": "(?:停下|停止|止住)", "words": [...] },
    "local":  { "count": 73,  "regex": "(?:...)", "words": [...] },   // 局部否定
    "scan":   { "count": 194, "regex": "(?:...)", "words": [...] },   // 时序/心理/情态
    "all":    { "count": 222, "regex": "(?:...)" }                    // 四类合并
  },

  "categories": [
    {
      "id": "A01",
      "name": "刀剑挥击破空",
      "domain": "A",
      "domainName": "冷兵器战斗",
      "effectCount": 19,
      "classifyRegex": "",            // ★待填：正向，段落属于本类
      "blockRegex": "(?:两面三刀|...|切菜|...|手术|...)",  // 本分类特有禁止
      "blockWordCount": 84,
      "blockWords": {                 // 按来源保留，便于维护
        "global": ["切菜","厨房",...],  // 原 ^(?!.*?(...))
        "tail":   ["中断","停歇"],      // 原 (?!.*(...))
        "scan":   [...],               // 原 (?:(?!(...))[^..])*
        "local":  [...]                // 原 (?! [^？?]*? (...))
      },
      "keywords": ["挥空","破空",...], // 仅用于生成初版映射
      "exclude": []                   // 仅用于生成初版映射
    }
  ]
}
```

> `keywords` / `exclude` **运行时不使用**，它们只是当初自动打标生成初版映射用的。
> 真正在跑的是 `classifyRegex` 和 `blockRegex`。

**运行时判定顺序**（先通用后特有，命中即淘汰该分类）：

```
段落 ──► commonBlock.all 命中？ ──► 是 → 淘汰
              │ 否
              ▼
        该分类 blockRegex 命中？ ──► 是 → 淘汰
              │ 否
              ▼
        classifyRegex 命中？ ──► 否 → 淘汰；是 → 该分类存活
```

### 4.2 `ai_effect_category_map.json`

```jsonc
{
  "total": 3830,
  "regexCount": 3830,
  "uncovered": ["空间挤压感", ...],          // 尚未归入任何分类的音效
  "effects": [
    {
      "name": "刀剑挥空",                     // 语义基名（已去掉题材版本号）
      "categories": ["A01"],
      "files": ["01_通用母库/硬音效/刀剑挥空.mp3", "11_战争打斗/硬音效/刀剑挥空2.mp3"],
      "regex": "(?:刀剑挥空|刀剑|挥空)",       // 本音效的匹配正则
      "regexSource": "generated"              // generated | reused
    },
    {
      "name": "切菜",
      "categories": ["N01"],
      "regex": "(?:(?:(厨房|下厨|正在|...)[^？?]{0,20}?(?:切了|切着|切|剁|...))|...)",
      "regexSource": "reused",
      "refRule": "切菜声"                     // 复用自哪条大正则
    }
  ]
}
```

`files` 里的路径即 `AiEffectDownloader.obtain(relativePath)` 所需的相对路径，
与 `AiEffectIndex` 的目录结构一致。

### 4.3 音效匹配正则怎么来的

**3830 / 3830 已全部生成**，两种来源：

| 来源 | 数量 | 做法 |
|---|---|---|
| `reused` | 61 | 音效名与大正则规则名 `Jaccard ≥ 0.5`，直接复用该规则的主体正则 |
| `generated` | 3769 | 按音效名自动生成：`全串 \| 首2字 \| 尾2字` |

**为什么复用率只有 1%**：两套命名体系差异太大。实测相似度分布：

```
sim = 1.0  : 14 个（完全同名，如「拧毛巾」「真气运转」「御剑飞行」）
sim ≥ 0.5  : 61 个（1%）
sim 0.2~0.35: 噪声居多（「剪指甲一下」←「拍一下」，只是都带「一下」）
sim < 0.1  : 2909 个（76%）
```

所以只能高相似的复用，其余自动生成。

**自动生成的规则**：先剥掉属性后缀，再取 `全串 / 首2字 / 尾2字`

```
刀剑挥空        -> (?:刀剑挥空|刀剑|挥空)
内力运转        -> (?:内力运转|内力|运转)
马嘶一声        -> (?:马嘶)              剥掉「一声」
切菜三刀        -> (?:切菜)              剥掉「三刀」
学校下课铃远景   -> (?:学校下课铃|学校|课铃)
倒水并喝水      -> (?:倒水并喝水|倒水|喝水)
```

> 用**首尾 2 字**而不是全部 2-gram：全部 2-gram 会产出跨词边界的无意义片段
> （`倒水并喝水` → `水并`、`并喝`），首尾取法能正确得到「倒水」「喝水」。

**复用时删掉了 bug 部分**：大正则主体的开头是
`^(?:[^“”「」？.?!])*`（把双引号/问号当硬边界，见 6.3）。
它不是预查，删预查时躲过了，复用流程里单独补删。

## 5. 怎么改

### 5.1 改单个音效的分类 → `tools/manual_overrides.json`

**不要直接改 `ai_effect_category_map.json`**，重跑脚本会被覆盖。

```jsonc
{
  "effects": {
    "重拳入肉":     { "set": ["A03", "A05"] },
    "大理石皮鞋一步": { "add": ["D03"] },
    "倒车雷达一声":  { "remove": ["F02"], "add": ["I03", "K06"] }
  }
}
```

- `set` — 完全覆盖（优先级最高）
- `add` / `remove` — 增量增删

改完执行：

```bash
cd tools && python3 export.py
```

### 5.2 改一批音效的分类（补关键词）→ `tools/category_rules.py`

未覆盖的 1565 个音效大多能用关键词批量捞回来，改这里最省事：

```python
'D03_脚步行走': (['脚步','走路', ...], []),
#                    ↑ 正向关键词        ↑ 排除词
```

例如补上「材质 + 步态」组合，能一次性覆盖 `木地板赤脚缓慢一步`、`瓷砖运动鞋正常一步`、
`大理石皮鞋一步` 这一大批：

```python
'D03_脚步行走': (['脚步','走路','行走','一步','两步','三步','几步','赤脚',
                  '皮鞋','靴','运动鞋','拖鞋','踮脚','跺脚','走廊','楼梯'], []),
```

### 5.3 新增 / 删除 / 改名分类

新增：在 `category_rules.py` 里按域字母加一行，ID 取同域下一个序号：

```python
'A07_暗器破空': (['暗器','飞镖','袖箭'], []),
```

同时若域名下新增了域，记得在 `DOMAINS` 里登记。

改名 / 删除：改 `category_rules.py` 的 key 即可，注意同步
`manual_overrides.json` 里引用到旧 ID 的条目。

### 5.4 重新生成

```bash
cd tools && python3 export.py
```

输出会打印：分类数 / 音效数 / 覆盖率 / 未覆盖数 / 手工覆盖条数。

## 6. 下一步：填正则（重点工作）

120 个分类的 `classifyRegex` 和 `blockRegex` 目前都是空的。

### 6.1 `classifyRegex` — 正向，这段属于我吗

用**词表组合**而不是单词，避免误命中：

```
(刀|剑|刃|兵器|长枪|匕首)[^。！？]{0,15}?(挥|斩|劈|砍|扫|刺)
```

### 6.2 `blockRegex` — 反向，命中就淘汰本分类（**已提炼完成 83/120**）

不是拍脑袋写的，是从 `ttsrv-replaces3.json` + `ttsrv-replaces5.json` 的
**1053 条成熟大正则**里程序化抽出来的。抽取逻辑见 6.4，结果落在
`tools/block_source.json`，由 `export.py` 合并进 `blockRegex`。

提炼结果的质量（都是真实踩过的坑）：

| 分类 | 禁止词 | 挡掉的错误 |

### 6.3 从大正则里抽了什么、没抽什么

`ttsrv-replaces3.json` / `ttsrv-replaces5.json`（远端 `cnb.cool/mingwuyan/yinpin/`）
共 1053 条音效规则，每条都自带排除结构。映射关系：

| 巨正则里的部分 | 抽到哪 |
|---|---|
| `^(?!.*?(古语\|俗话\|抽烟\|…))` | `blockWords.global` / `commonBlock.global` |
| `(?:(?!(想\|回忆\|如果\|从未\|…))[^“”「」？.?!])*` | `blockWords.scan` / `commonBlock.scan` |
| `(?![^？?]*?(无法\|没能\|…))` | `blockWords.local` / `commonBlock.local` |
| `(?!.*(落定\|不染))` | `blockWords.tail` / `commonBlock.tail` |
| `(刀\|剑\|…)[^？?]{0,15}?(脱手\|掉落\|…)` | **不抽**，这是音效匹配正则，留给第 ③ 层 |

#### ⚠️ 明确不抽的部分（原作者的 bug）

逐字扫描结构里的字符类 **`[^“”「」？.?!]`** 被**丢弃**，不进任何 `blockRegex`：

```
(?:(?!(?:想|记忆|回忆|…))[^“”「」？.?!])*
                          ^^^^^^^^^^^^^^
                          这一截不抽
```

它把双引号和问号当成硬边界，扫描一旦碰到就中断，导致：

- **引号内的内容匹配不到** —— `他抽出长剑，喝道："受死！"` 引号后的动作全部漏配
- **疑问句后的内容匹配不到** —— `你听见了吗？刀已出鞘。` 后半句漏配

这是原作者为了防跨句误报做的妥协，代价是大量漏报。
我们的三层架构里，句子边界由**切句**处理，不靠字符类硬拦，
所以这部分既不抽、也不该在新正则里复现。

同样不抽的还有 `(?<!\()(?!\()`（防重复插入标记），那是文本替换阶段的产物，
新方案直接产出 `AiEffectPick` 结构，不需要在文本里插标记。

### 6.4 抽取与归类流程

```
1053 条规则
   ├─ 括号配对提取所有 (?! …) 负向预查
   ├─ 按前缀分类：  .*?(?:  → global
   │               .*(?:   → tail
   │               [^？?]*?(?: → local
   │               (?:     → scan
   ├─ 词频统计：出现在 ≥50% 规则里 → 通用集（222 词去重）
   │            其余 → 该规则所属分类的特有集
   └─ 规则名 → 分类：用 category_rules.py 的关键词匹配
                （先原样，再去掉「人 / 众 / 一下」等主语前缀重试）
```

- 规则名 → 分类：489 / 1053 命中，归集出 **83 个分类**的特有禁止词
- 未映射 289 条（多为「18+」与人物细碎动作，如 `人亲吻`、`人打呼噜`），
  清单在 `tools/block_source.json` 的 `unmapped` 字段，可手工归类后重跑

### 6.5 通用集的分类豁免（**已实现**）

`commonBlock` 里的 222 个词全是**假设 / 时序 / 心理 / 否定**词
（`如果|曾经|回忆|梦里|心中|无法|早已`…），并非对所有分类都成立：

- `E08 记忆回忆` 的段落**必然**含 `曾经 / 当年 / 想起`
- `E09 幻觉梦境` 的段落**必然**含 `梦里 / 心中`
- 若不豁免，这两个分类会被通用集团灭，永远匹配不到

#### 机制：正向词自动豁免 + 手工补充

```
对分类 C：
  正向词集 P = C.classifyRegex 的词
  总禁用集 G = commonBlock.all
  自动豁免   = { w ∈ G | w 与 P 中某个词有子串重叠 }
  最终豁免   = 自动豁免 ∪ C.commonExempt（手工补）
  有效禁用   = (G − 最终豁免) ∪ C.blockRegex
```

即**正向词自动获得对总禁用的豁免权**，不用手工维护整张豁免表。

#### ⚠️ 豁免只认一个方向：`禁用词 ⊆ 正向词`

```
E08 正向「记忆深处」 → 禁用「记忆」失效      ✅ g ⊆ p，豁免
E08 正向「回忆」     → 禁用「回忆」失效      ✅ g ⊆ p（相等），豁免
A01 正向「用」       → 禁用「用来」不失效    ❌ p ⊆ g，不豁免
```

反向（`正向词 ⊆ 禁用词`）**必须排除**。否则单字正向词会吃掉一长串禁用词：
`A01` 正向有单字「用」，一旦允许 `p ⊆ g`，`用来 / 用作 / 用于 / 作用为 / 作用是`
会被全部豁免，该分类的禁用保护直接失效。

实测：允许双向时有 37 个分类产生豁免（大量是错的），
改成单向后降到 10 个，且全部合理。
这类语义豁免改由 `manual_block.json` 的 `exempt` 显式声明。

自动算不出的语义豁免，在 `tools/manual_block.json` 里用 `exempt` 字段手工补：

```jsonc
"E08": {
  "classify": ["记忆","回忆","回闪","闪回","追忆","想起",...],
  "block":    ["记忆卡","U盘","存储","记性",...],
  "exempt":   ["梦中","梦里","曾经","从前","当初","当年","当时","早已",...]
}
```

### 6.6 推荐执行顺序（省性能）

```
120 条 classifyRegex（正向词表，便宜，可倒排预筛）→ 命中 3~8 个分类
      ↓
只对这几个跑 blockRegex（含否定/时序结构，较贵）  → 剩 1~3 个分类
      ↓
只对这几个分类下的音效跑匹配正则               → 几十条
```

反过来先跑 120 条 blockRegex 会贵一个量级。

## 8. 踩坑记录

### 单字关键词误伤极其严重

第一版用单字打标，命中率虚高 76% 但全是错的：

| 关键词 | 误命中 |
|---|---|
| `马` | 抽水马桶、马桶冲水、马达 |
| `雷` | 倒车雷达、手雷拉环、地雷 |
| `鸡` | 打鸡蛋 |
| `石` | 大理石皮鞋、碎石 |
| `沙` | 沙发、沙发坐下 |
| `铁` | 地铁报站 |
| `御` | 御剑破空（本该是 C09，混进朝堂官府） |
| `电` | 电话、电视、电梯、电脑 |
| `箱` | 语音信箱、冰箱 |

**结论：每个分类的关键词表必须配 `exclude`**，这和给每个分类配 `blockRegex` 是同一个道理。

### 音效名有两套体系，对接不上

- 规则侧（`ttsrv-replaces*.json`）：`山体崩碎`、`刀剑掉地`、`一箭破空`（动作视角）
- 音效库侧：`岩石崩碎`、`刀剑挥空`、`御剑破空`（声音事件视角）

语义相关但字符串不同，实测直接命中率仅 **2%**。
好在本分类体系是按语义重建的，**音效 → 分类** 与 **分类 → 文本正则** 解耦后，
两套命名不需要字符串对齐，各自映射到分类即可。

### 同一音效存在多个题材版本

`丹田发热` / `丹田发热2` / `丹田发热3`…分别属于玄幻、仙侠、武侠、古风版。
映射文件里 `name` 存语义基名，`files` 存全部版本路径，
运行时按当前书籍题材挑对应版本（待实现）。
