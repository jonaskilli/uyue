## 二、角色认领：只认「当前这一句」完全匹配

**状态**：本地已改，未推送（已进入 16:27 包）。

### 极端情况

- 一段里有多对双引号；或相邻段落出现完全相同的短对白（「嗯。」「好。」「不行。」）。
- 从第三章合成到一半，退回第二章删掉某段音频重新合成；`reading_progress.json` 仍停在第三章的 `lastSeq`。
- 角色缓存里某条的 `dialogText` 因为跨段识别存成了多行文本。

### 错误表现

双引号上方已经显示出正确的说话人（例如女青年），但合成音频用的是另一个人的音色（例如男声）。删掉该段音频重新合成有时仍是错的；翻页／重启后再删再合成才恢复正常。

### 原因

`matchInChapterCacheBySeq(chapterTitle, predictedSeq, cleanCurrent)` 原来按 `[0, +1, -1, +2, -2]` 浮动找序号，并且用 `tryMatchTextWithNewlines` 允许缓存里多行文本的**任一行**匹配就返回该条角色。于是预测序号偏了之后，会在邻域里找到一句文字相同、但属于别的段落的角色，直接拿来配音色。`useProgress` 分支只要本段所有对话都在邻域里蒙到，就采信且不再定位。

### 修复方法

`matchInChapterCacheBySeq` 改为只认一条：

```js
var cachedItem = results[String(predictedSeq)];
if (!cachedItem) return null;
var dialogText = cachedItem.dialogText;
if (dialogText && cleanDialogText(dialogText) === cleanCurrent) return cachedItem;
return null;
```

- 去掉 ±2 浮动邻居认领；
- 去掉「缓存多行文本任一行匹配」，改为整条 `dialogText` 经 `cleanDialogText` 清洗后与当前句**全等**；
- 取不到返回 `null`，由主流程降级重新定位或走 AI，不拿邻居角色顶替。

## 三、进度指针：只作辅助，必须与当前段定位一致

**状态**：本地已改，未推送（已进入 16:27 包）。

### 极端情况

`reading_progress.json` 记的是「合成顺序」，不是真实的上一句。典型操作：第三章合成到某句 → 停止 → 返回第二章 → 删掉一个音频 → 重新合成。切**书**会清空进度与段落历史，**切章不会**。

### 错误表现

脚本仍按 `progress.lastSeq + 1` 预测当前句的引号序号，并用 `progress.chapterTitle`（第三章）去读第三章的角色缓存；当前合成的是第二章，序号与章节全都不对。删除音频不会重置进度和 `paragraphHistory.json`，所以反复重合成会重复同一个错误音色。

### 修复方法

`useProgress` 生效前增加硬校验：先用**当前正在合成的段落文本**做一次全文定位，只有三项全对才允许按进度继续。

```js
if (useProgress) {
    var verify = locateParagraphInFullText(originalText);
    if (!verify || verify.chapterTitle !== progress.chapterTitle
        || verify.seqList.length < dialogs.length
        || verify.seqList[0] !== progress.lastSeq + 1) {
        useProgress = false;
    }
}
```

`useProgress = false` 后主流程自然走 `locateParagraphInFullText` 分支重新算序号。上一段历史（`locateByPrevAnchor`）只用来缩小候选，它本来就要求当前段 `substring === paragraph` 精确相等，不再单独拍板。

## 四、meta 定位：标题 + 段落号 + 当前段文本比对

**状态**：本地已改，未推送（已进入 16:27 包）。

### 极端情况

`ttsMeta` 里发的 `chapterTitle` 与 `dialogSeqs` 来自 Kotlin 的 `contentList`；脚本读的 `data.json` 是另一份文本。两条合成路径的段落列表也不同：播放路径用 `contentList`，预下载路径用重新 `split("\n")` 出来的 `segments`。段落切分或引号数量一旦不同，`dialogSeqs` 整体偏位。

### 错误表现

段落号定位看起来"成功"了，但取出来的对话序号不对，导致 `matchInChapterCacheBySeq` 匹配失败 → 走 AI 重新识别，并且可能用偏掉的 `realSeq` 写回缓存，污染后续识别。

### 修复方法

`getFixedLocationFromMeta(paragraph)` 在采信 `dialogSeqs` 之前，先做三级确认：

1. `getTtsMeta()` 容错读取（旧版本没有 `ttsMeta` 绑定直接返回 `null`）；
2. 按 `meta.chapterTitle` 在 `data.json.texts` 里逐行找到标题行，收集标题之后的本章段落行（遇到下一个无缩进行即停止）；
3. 按 `meta.paragraphIndex` 取候选段落，`cleanDialogText(候选段) === cleanDialogText(当前段)` 才通过。

另外开头还校验 `meta.paragraphText` 与当前段是否一致。任何一步不满足都返回 `null`，交给 `locateParagraphInFullText` 的降级链，**不采信脏 meta 的序号**。

> 说明：`dialogSeqs` 与 `reading_progress.json` 的 `lastSeq` 是同一套编号（本章内左双引号序号）；`paragraphIndex` 是章内段落下标，两者不是一回事。缓存的 `results` 键按引号序号排，所以「段内第几句」必须靠累计左引号数定位，段落号本身做不到。

## 五、AI 识别的上下文：接入同一套定位

**状态**：本地已改，**未进入任何 APK，也未推送**。

### 极端情况

定位成功但角色缓存里没有已识别的名字时，主流程会调 AI 识别。此时 `getAboveContext` / `getBelowContentInfo` 只拿到 `originalText`，原来是在 `data.json.texts`（**多章拼接的全文**）上做单段 `indexOf`：

- 当前段文字在前面章节重复出现 → 命中第一次，上文／下文取成别的章的内容；
- `getPrevParagraph()` 取的是合成历史，跳章重合成时是错的 → 联合锚点失败 → 退回 `indexOf`；
- 退回上一章且 `data.json` 未重写时，当前章根本不在 `data.texts` 里 → 上文、下文全空。

### 错误表现

发给 AI 的「上文 1000 字 + 当前段编号对话 + 下文 1000 字」不是当前段的真实上下文；`generateBatchSeqContent` 编号的后文句子不是真正的后文；`buildCrossChapterResults` 用 `belowInfo.startPos` 计算跨章 `realSeq` 时，把角色写进错误的章节或错误序号，污染缓存。

### 修复方法

新增 `locateParagraphByMeta(paragraph)`：用「章节标题 + 段落号 + 当前段文本」在 `data.json` 里定位，逐行在原串推进算出**真实字符偏移**，返回 `{ startPos, endPos, chapterTitle, fullText, chapters }`。

- `getAboveContext`：优先用 `located.startPos` 往前取 1000 字；失败才退回 `indexOf(当前段)` → 前 50 字。
- `getBelowContentInfo`：优先用 `located.startPos` / **`endPos`** 取后 1000 字，`chapters` 也用定位时算好的；失败才退回 `上一段历史联合锚点 → 单段 indexOf → 前 50 字`。
- 用 `endPos`（定位行的实际末尾）而不是 `targetPos + currentParagraph.length`：段首缩进、从段落中间起读时两者长度不同，会让下文起点偏掉，进而让 `startPos` 和跨章 `realSeq` 跟着偏。

这样 `seqList`、AI 上下文、`belowInfo.startPos`、跨章写入的引号序号全部出自同一个位置。

## 六、章节名口径统一（Kotlin 侧）

**状态**：本地已改，未推送（已进入 16:27 包）。

### 极端情况

章节标题被「标题替换规则」改过时，同一个章节同时存在三套名字：

| 用途 | 原来的名字 |
|---|---|
| `data.json` 每章第一行 | `chapter.getDisplayTitle(getTitleReplaceRules())`，即 `displayTitle` |
| 角色识别 json 文件名 | 原始 `BookChapter.title` |
| `ttsMeta.chapterTitle` | 播放路径回退 `textChapter.title`（displayTitle）；预下载路径传 `chapter.title`（原始） |

### 错误表现

脚本拿 displayTitle 去 `readChapterCache()` 读按原始名命名的 json，读不到文件 → 取不到角色 → 走「群众／男男青年」兜底（男声）；而阅读界面标注读缓存用原始 `ch.title`，能正常显示女青年。**标注对、合成错**，且只在标题被替换规则改过的章节出现。

### 修复方法

三处统一成原始 `BookChapter.title`（已有识别结果都按它命名，改它成本最低、不丢数据）：

1. `ReadBook.saveTtsTextJson`：写 `data.json` 时，把每章净化结果的第一行替换为 `ch.title`（去掉换行），正文仍保持逐章净化后拼接，不把多章拼好再统一净化。
2. `BaseReadAloudService.buildTtsMetaJson`：`title` 优先取传入的 `chapterTitle`（预下载路径已传原始名），没有则取 `textChapter?.chapter?.title`（播放路径当前章原始名），**不再用 `textChapter.title`**。

装新包后第一次开始朗读会 `saveTtsTextJson(force = true)` 重写 `data.json`，新口径即生效；已有角色 json 无需重建。

## 七、定位与降级链总览（最终形态）

```
合成一段
  ↓
读 reading_progress.json（bookName / chapterTitle / lastSeq）
  ↓ 先用当前段全文定位校验：章节一致 且 lastSeq+1 == 定位出的首句序号
  ├─ 一致 → 进度路径：predictedSeq = lastSeq+1+i
  │          matchInChapterCacheBySeq：指定序号 + 当前句完全相等才认
  │          全部命中 → 直接采用；任一不命中 → 降级
  └─ 不一致 → 禁用进度，强制定位
                ↓
        locateParagraphInFullText
          1) getFixedLocationFromMeta：章节标题 + 段落号 + 当前段文本比对
          2) locateByPrevAnchor：上一段历史（必须在前）+ 当前段（必须在后）精确匹配
          3) fullText.indexOf(当前段)：找第一个出现
          4) 前 50 字 indexOf
          5) 章内重新定位 → 数段前左引号 beforeCount → seqList
          6) 全部失败 → 群众／男男青年默认音色
                ↓
        缓存缺名字 → 调 AI
          locateParagraphByMeta 定位当前段
          → 上文 1000 字 / 下文 1000 字 / startPos / chapters
          → 定位失败则退回 2)3)4) 老链
```

**唯一硬条件**：无论哪一级定位，认角色的最后一道关永远是「当前正在合成这一句的文本 === 缓存里该序号的 `dialogText`」。不满足就降级，不浮动认领邻居。

## 八、兼容旧版本 APP

所有新增入口都以 `getTtsMeta()` 开头，容错顺序一致：

| 情况 | 处理 |
|---|---|
| 旧版本没有 `ttsMeta` 绑定 | `typeof ttsMeta === "undefined"` 先判空（typeof 对未声明变量安全，不抛 ReferenceError），再 `try/catch` → 返回 `null` |
| `chapterTitle` 为空 | 返回 `null` |
| `paragraphIndex` 缺失 / NaN / 越界 | `parseInt` + 范围检查 → 返回 `null` |
| `paragraphText` 与当前段不符 | 返回 `null` |
| 标题在 `data.json` 找不到、候选段文本比对不一致 | 返回 `null` |
| 新函数内部任何异常 | 整段 `try/catch` → 返回 `null` |

返回 `null` 后一律走原有降级链，不会报错、不会卡死。

**行为变化（非兼容问题）**：`useProgress` 的前置校验不依赖 `ttsMeta`，旧版本上也会执行；若彼时 `data.json` 未覆盖当前章，会禁用进度快路径，多走一次定位或 AI 请求。老包写进 `reading_progress.json` 的 `chapterTitle` 可能是 displayTitle，与新口径不一致时也会让首段降级，等 `writeProgress` 用新标题重写一次后恢复正常。不会配错音色。

## 九、Z3.3 升级：跨章节保存与其他已推送修复

`9fead18`（11-08 22:44）和 `61b755d`（11-09 00:13）的提交标题很简短，**详细修复项写在 commit body 里**，容易被只看标题的记录漏掉。这两笔已推送，最终留在代码里的内容如下。

### 9.1 跨章节识别结果不再被舍去

- **极端情况**：一次 AI 识别会把「当前段对话 + 段后 1000 字下文里的对话」一起编号送去判断（竞速与上下文需要）。章末段落的下文往往已经跨进下一章。
- **错误**：旧版只把当前段（`p < currentCount`）的结果写回当前章缓存，**跨到下一章的识别结果直接舍去**；本次已经花请求识别出来的角色全部丢掉，合成到下一章时还要再问一次 AI，章首／章末角色更容易缺失。全书分析侧同样存在「跨章预取结果不落盘」的问题。
- **修复**：`9fead18` 引入三个函数，把结果按章节分组落盘：
  - `buildCrossChapterResults(...)`：前 `currentCount` 条按 `seqList[p]` 写当前章；之后的句子用 `belowInfo.startPos + bd.sourceOffset` 算出在 `data.json` 全文里的绝对位置，在 `getChaptersFromFullText` 的章节列表里定位目标章节，数该章 `beforeText` 中的 `“` 得到 `realSeq`。
  - `addChapterResult(groups, names, chapterTitle, realSeq, aiInfo, dialogText)`：按章节名分组累积 `results[realSeq]`。
  - `mergeChapterResultGroups(groups)`：逐章 `mergeChapterResults(title, ...)`，分别写进各自的 `<章节名>.json`。
  - 解析不到章节时用 `lastCurrentRealSeq + 1 + belowIndex` 兜底，并用 `locationTotalDialogs` 限制序号不越过本章范围、不污染当前章缓存。
  - 全书分析侧 `BookScriptAnalysisService` 同步增加「跨章预取结果落盘、轻量跳章、进度统计优化」。
- **配套**：章节缓存写入改为**数字序号升序 + 两空格缩进**（`JSON.stringify(cacheData, null, 2)`），便于人工排查。

### 9.2 上一段锚点的缩进兼容

- **极端情况**：`data.json` 的正文段落带全角空格缩进，而传入的当前段可能没有缩进，或两段之间夹着空行／空格。
- **错误**：单段 `indexOf` 匹配不到，联合定位失败 → 退回全文第一个匹配 → 重复段落定位到错误位置，`beforeCount` 全错。
- **修复**：`locateByPrevAnchor` 支持两种情况：两边都带同样缩进时直接 `substring === paragraph`；否则跳过最多 16 个空白字符后按「去缩进的当前段」比对，并尽量返回带缩进的真实起点，保证调用方 `targetPos + paragraph.length` 不错位。

### 9.3 发音人来源与编号

- **极端情况**：外部 `fayinren.json` 里新增了内部表没有的发音人标签；或一章对话编号超过两位数容量。
- **错误**：外部标签被内部表取交集过滤掉；局部序号宽度不够时编号冲突。
- **修复**：`fayinren.json` 读取成功且能提取出可用标签时**完全采用外部标签**，不再与内部表取交集；局部序号支持 1~4 位（专用分析脚本同步），三位发音人编号正常工作。

### 9.4 ttsMeta 可选与老版本回退

- **极端情况**：脚本被贴在旧版本 APP 上使用，Kotlin 侧没有注入 `ttsMeta` 绑定。
- **错误**：硬读未声明变量会直接让脚本执行失败。
- **修复**：朗读服务把 `ttsMeta` 作为**可选**绑定注入；脚本 `getTtsMeta()` 用 `typeof ttsMeta === "undefined"` + `try/catch` 容错，读不到返回 `null`，自动回退旧的全文定位。后来所有 meta 定位修复能兼容旧包，基础就在这里。

### 9.5 五阶校验式竞速（`61b755d`）

- **极端情况**：多组 API 竞速时，某个接口返回 HTTP 200 但内容是错误页、JSON 解析失败，或字段／序号不全。
- **错误**：旧 3 阶逻辑把「连接成功但业务失败」当成有效结果，抢先停止其它阶梯，明明后面还有正确结果却整段识别失败或角色错乱。
- **修复**：新增 `ajaxRaceDelayedValidated`，请求从 3 阶改为 5 阶；只有**合法业务结果**（字段齐全、序号合法）才算成功并停止其它连接，连接错误／HTTP 错误／JSON 解析失败／字段或序号不全时立即放行下一阶；单请求超时 25 秒，请求携带 `timeout / validScene / validExpected`。

## 十、已推送部分：净化与专用脚本口径（最终形态）

### 净化开关必须生效

- **极端情况**：在阅读界面右上角勾选／取消「双引号修复」或「重新分段」，或全书分析取后续章节正文时。
- **错误**：`data.json` 仍是旧文本（因为节流只看书名和章节），朗读与全书分析用不上新勾选；或专用脚本取到的正文与阅读界面口径不同。
- **修复**：`ReadBook.cleanContentForTts` 显式传 `fixQuote = book.getFixQuote()`、`reSegment = book.getReSegment()`；`saveTtsTextJson` 的节流条件加入两个开关状态，勾选变化即重新净化写入。执行顺序由 `ContentProcessor` 保证：先 `QuoteFix.fix`、再 `ContentHelp.reSegment`、然后简繁和替换净化。**每章单独净化后再拼接**，绝不把多章拼成一整串再统一净化。

### 全书分析专用脚本的编号口径对齐内置 Z3.3

- **极端情况**：章节超长按字数分块并发请求；对话前后有叙述文字；一段含多对双引号。
- **错误**：专用脚本原先只把引号**内部**文字抽出来编号、把 1000 字下文里所有对话全部编号要求 AI 判断，丢失「张伟摇了摇头」「李娜追问道」等说话人提示，识别率明显低于逐段朗读；姓名／别名提示词与内置 Z3.3 还差一个换行。
- **修复**：`bookAnalysisScript.js` 的 `_buildSeqContent` 按 `generateBatchSeqContent` 重写——当前段对话重包引号 + 下文 1000 字**原文**（保留叙述）、补右引号、只给前 80%（≤5 句全给）的左引号编号，尾部留作只供参考的上下文；别名提示词补齐换行与内置一致。
- **写回时机**：分块并发全部返回后才按预先算好的偏移汇总，整章一次性写回，不会每块单独写；任一块失败则整章不写。

## 十一、验证方式

- 两个脚本 `node --check` 语法通过；内置 `ttsScripts.json` 的 `code` 与根目录 `朗读脚本Z3.3需要密钥.js` 逐字一致。
- 定位校验用例：标题+段落号+文本一致 → 通过；段落号偏一位／章节标题错／段落号越界 → 拒绝并降级。
- 严格匹配用例：缓存 10 是男声「不行。」、缓存 11 是女声「真的不行。」、当前句「不行。」预测序号 11 → 旧实现会浮动到 10 认领男声，新实现返回 `null` 走降级；精确命中时仍能取到女声。

- 正式版打包：`BUILD SUCCESSFUL`，`apksigner verify` → `Verifies`（v1/v2/v3 全 `true`）。
